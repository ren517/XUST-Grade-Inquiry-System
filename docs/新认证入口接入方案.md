# 新认证入口接入方案

目标：保留老教务系统登录逻辑不变，新增一个新认证入口，只用它完成登录并拿到有效 cookie，之后原有成绩查询、历史对比、Excel 导出逻辑原样复用。

---

## 一、结论

**已经跑通。** 学号 24407120135 实测：新入口登录 → 拿到 `JSESSIONID` + `route` → 成绩查询 13 门课 → 历史对比 → Excel 导出 → 二次运行 cookie 缓存复用，全部正常。

改动面很小：`login.py` / `score.py` / `history.py` / `crypto.py` 一行未改，只新增了入口模块，`main.py` 和 `cookie_manager.py` 是向后兼容的小改。

```bash
python main.py                # 老入口，行为与改造前完全一致
python main.py --entry=jwsso  # 新入口
```

## 三、新入口：教务系统的 CAS 通道

关键点在于，**老教务系统本身就有 CAS 认证入口**，只是藏得深：

```
GET http://59.74.174.150/jwglxt/auth/auth_casAuthLogin.html
 → 302 http://jwsso.xust.edu.cn/auth/cas/login?service=http%3a%2f%2f59.74.174.150%2fjwglxt%2fauth%2fauth_casAuthLogin.html
```

教务门户里每个应用（成绩查询、课程表、学生选课……）的链接都是这个入口加 `url=` 参数，例如成绩查询：

```
http://59.74.174.150/jwglxt/auth/auth_casAuthLogin.html?url=%2fcjcx%2fcjcx_cxDgXscj.html%3fgnmkdm%3d...
```

### 完整链路（已实现）

```
1. GET  /jwglxt/auth/auth_casAuthLogin.html          → 拿到 jwsso 的 CAS 登录地址
2. GET  该地址?login_type=normal&login_type_fragment=ImplNormal → 取 __token__
3. POST 该地址?login_type=normal
        username / password / __token__ / fingerprint
4. 302 → /jwglxt/auth/auth_casAuthLogin.html?ticket=ST-xxx
5. 302 → /jwglxt/ticketlogin?uid=...&verify=...&jsdm=xs
6. 302 → /jwglxt/xtgl/index_initMenu.html            → 会话建立，拿到 JSESSIONID + route
```

### 密码加密（第一版踩的坑）

AES-128-CBC + ZeroPadding + Base64，**key 与 iv 都取当前 `__token__` 的前 16 位，每次请求都变**。写死常量必然登录失败。

```
key = iv = token[:16]
明文 = password.strip()，不足 16 字节补 \x00
```

`fingerprint` 是 FingerprintJS 的 visitorId，服务端只记录，随机 32 位十六进制即可。

### 另一个坑：系统代理

本机有 TUN 代理（`127.0.0.1:54061`）时，**访问教务的 CAS 端点会返回 503**，直连正常。所以 `JwssoLogin` 里设了 `session.trust_env = False`。老入口不受影响（保持原样）。

## 四、模块清单

| 文件 | 类型 | 说明 |
| --- | --- | --- |
| `login.py` | 未改 | 老 `JWXTLogin` 原样保留 |
| `score.py` / `history.py` / `crypto.py` | 未改 | 后续逻辑原样复用 |
| **`jwsso_login.py`** | 新增 | `JwssoLogin(JWXTLogin)`，CAS 全流程，只覆盖 `login()` |
| `ids_login.py` | 新增 | 备选：ids.xust.edu.cn 的 CAS 入口（参数已摸清，但该通道未注册教务回调） |
| `cookie_manager.py` | 小改 | cookie 文件名加 entry 前缀，老签名完全兼容 |
| `main.py` | 小改 | 入口选择，默认 legacy |
| `verify_login.py` | 新增 | 四项断言的验证脚本 |
| `explore_jwsso.py` | 新增 | 登录后看有哪些应用入口 |

### 统一契约

两个新类都继承 `JWXTLogin`，天然具备 `session` / `base_url` / `check_login()`，只需保证：

> `login(username, password)` 返回 True 后，`self.session` 里必须有 59.74.174.150 域的 `JSESSIONID` 与 `route`。

这条成立，`select_score()`、`history` 全部照旧。

### 兼容老入口

1. **默认 legacy**。`python main.py` 与改造前逐字一致，cookie 仍是 `cookies/<学号>.json`。
2. **缓存按入口隔离**：新入口写 `cookies/jwsso_<学号>.json`，不覆盖老缓存。
3. **入口三档覆盖**：默认 legacy → 用户 JSON 加 `"entry": "jwsso"` → 命令行 `--entry=jwsso`（优先级最高）。
4. **失败可回退**：`--entry=legacy` 跑一遍即可。

## 六、过程中的排查手法（可复用）

1. **加密对不对**：用 Node 内置 crypto 与站点自己的 JS 做双向验证；再用"加密 16 个零字节"提交，服务端返回"密码不能为空"就说明解密链路正确，且这条路径**不消耗失败次数**（校验顺序是：密码判空 → 用户是否存在 → 密码比对）。
2. **找隐藏端点**：从教务处官网的链接清单入手，比在认证服务器上盲猜 service 有效得多。本次就是靠官网链接发现了 `center_portal`，再从门户配置 `frontend/smilecampus_config.js` 和 `portal/base/get_config` 里的"教务应用" tab 反查出 `auth_casAuthLogin.html`。
3. **503 类故障先怀疑代理**：同一 URL 走代理 503、直连 302，用 `trust_env=False` 对比即可定位。

## 七、注意事项

- jwsso 有失败次数限制，超限会锁账号（"尝试登录次数过多，账号已被锁定，将于 xx:xx 解除"）。别用脚本连试错密码。
- 教务密码与统一身份认证密码相同，用户文件里已存的密码可直接复用。
- `ids_login.py` 走的是 ids.xust.edu.cn，该 CAS 对教务域回调返回"应用未注册"，目前仅作备选保留。
